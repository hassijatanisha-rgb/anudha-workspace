# Anudha workspace implementation rules

Fingerprint: based on `main` at `3405b5b` on 2026-09-21. Small-project full scan (12 source files).

## Golden Files

- `app.js` — global application state, authentication gate, route dispatch and small DOM helpers.
- `client-profile-pages.js` — page rendering as focused functions, escaped template output and event binding after render.
- `inventory-operations.js` — lazy feature loading, staff-facing workflow screens and RPC-only writes.
- `inventory-domain.js` — pure validation and quantity-planning functions that can be tested without the browser.
- `supabase/migrations/202609210001_inventory_foundation.sql` — database-enforced authorization, row locks, optimistic versions, immutable ledgers and atomic business transactions.
- `tests/inventory-schema.test.mjs` — lightweight structural tests that protect required database invariants.

## Naming & State-Control Rules

- Keep browser files as plain strict-mode JavaScript loaded by `index.html`; do not introduce a bundler or framework into this release.
- Use lower camel case for JavaScript functions and state. Use snake case only for database columns and Supabase RPC arguments.
- Keep feature state and rendering inside a dedicated feature file. Add only top-level navigation and dispatch hooks to `app.js`.
- Escape all database/user text with `esc()` before placing it in HTML templates.
- Bind handlers after each render and guard writes through the shared `run()`/busy behavior or a feature-local equivalent.
- Load large or specialized datasets only when their feature is opened. Do not add more all-record startup downloads.
- Put calculation and transition planning in pure functions when practical; keep network and DOM work at the edges.
- Send every business write through a `security definer` Supabase RPC. Browser code must not directly insert, update or delete workflow tables.
- Every mutable aggregate has a positive `version`; writes provide an expected version, lock authoritative rows and reject stale work.
- State transitions are forward and explicit. A UI button never substitutes for a database transition rule.
- Financial amounts are stored as integer minor units. Quantities that must be whole units are validated as safe integers.
- History, revisions and stock movements are append-only. Corrections create new versions or compensating records.
- Enable RLS on every exposed table, grant reads only to active authenticated staff and keep write privileges behind RPCs.
- Errors shown to staff explain the corrective action in plain language.

## DONTs

- Do not copy the old Next.js component structure into this static workspace; copy its verified business rules only.
- Do not invent clients, contacts, product mappings, prices, stock quantities, delivery proofs or acceptance references.
- Do not allow a Pro forma, delivery or stock record to skip its required predecessor.
- Do not let delivery forms issue unverified stock or bypass Haadi.
- Do not overwrite accepted customer-facing document revisions.
- Do not silently retry an uncertain write with a new identifier.
- Do not use client-side role checks as the security boundary.
- Do not add hard-coded employee limits or per-user copies of shared business records.
